The database that describes its own cluster — and survived being destroyed

NetBox is an infrastructure inventory, and ours holds the records of the very machines it runs on — site, cluster, VMs, prefixes, IPs, all discovered from the live cluster rather than typed. That self-reference is the point: every drill breaks something the database itself depends on, and "recovery" means those records come back.

Three loops keep it alive — traffic (you → Gateway → NetBox → Postgres), reconcile (git → Argo CD → everything), durability (Postgres → Azure Blob). Each drill attacked a different loop. All five passed; the database never lost a committed row. Click a drill for what actually happened.

The finding none of them were designed to produce: the cluster was almost never the problem. Every serious outage traced back to configuration or to the tools built to observe and deploy it — an unpinned secret, a lying resource request, a harness that measured nothing and reported numbers.

Traffic loop

Cloudflare resolves netbox.k8s.kahng.dev to a node; Envoy terminates TLS and routes to a NetBox pod, which talks SQL through the pooler to whichever instance is primary.

Reconcile loop

Argo CD watches git and keeps six Applications Synced/Healthy. Nothing is hand-applied — and drill 2 found the sharp edge: a child Application's spec is root's data, so pausing a child alone is reverted within seconds.

Durability loop

Every closed WAL segment ships to Azure Blob via the Barman Cloud Plugin (migrated 08-28, ahead of CNPG 1.31 deleting the in-tree path). Base backups every 6h. RPO: the currently-open segment.

What the card proved

Five drills, five journals. The database never lost a committed row. Every serious outage came from configuration or tooling — not from Postgres, and not from Kubernetes.

1 · Failover under load · passed

Result: 31.1s write gap · 8 failed requests of ~124 · zero rows lost

Fired

kubectl delete pod pg-1 — the primary — under 4 req/s of API load, with a probe writing a timestamped row every 500ms.

The surprise

The "dead" primary kept accepting writes for three more minutes. A graceful delete is a switchover: CNPG uses the termination grace to run an orderly handover. A real crash test needs --grace-period=0 or a lost node.

The pooler earned its keep

124 requests entered a 31-second window with no writable database; 116 succeeded. PgBouncer holds clients rather than refusing them, then replays onto the new primary.

Versus Patroni (7.3)

No election, no split-brain window to reason about: the operator decided, and the PRIMARY label moved exactly once. Centralized promotion, measured under load.

2 · Migrations at scale · passed, expensively

Result: migration innocent · 2,145 failed requests from our own config · 14× better after fixes

Fired

Two git commits: scale the web tier up, then upgrade the chart 8.3.46 → 8.3.57 (app v4.6.7 → v4.6.8) while pods served traffic.

The migration was a non-event

Applied exactly once, no observable lock contention at 3-second sampling. Django's own locking made the second pod's attempt a no-op. The feared part was free.

The delivery machinery was not

An unpinned chart secret (Valkey's password) rotated mid-sync, breaking every running pod's cache auth; and hard anti-affinity + surge rollouts deadlock when replicas equal nodes. Nine minutes of 500s, from two bugs of ours.

Bonus: the scheduler lesson

Scaling first killed a node outright. A memory request is a promise to the scheduler, and ours lied by 1GB — so it packed two booting pods onto one worker until its kubelet went silent. Requests now match reality; workers went 4→8 GB.

3 · Cache vs queue · both predictions wrong

Result: 22s of hard 500s · 62 failed requests · 5 of 5 queued jobs survived

Fired

kubectl delete pod netbox-valkey-primary-0, with five RQ jobs planted in the queue as bodies to count afterwards.

The queue survived

Expected total loss; got zero. Bitnami's Valkey ships appendonly on a PVC, and a StatefulSet pod returns as itself — the AOF replayed. The real RPO is ~1 second, not "the pod's lifetime".

The cache did not degrade

NetBox returned 500 for every request while Valkey was down — sessions and config caching are load-bearing. "It's just a cache" is false for this app. And on return, latency was instantly normal: the feared re-warm is a ghost at lab scale.

The hierarchy

Pod killed: 22s, self-healing, zero hands. Password rotated (drill 2): 9 minutes, all pods, manual twice. Infrastructure death is cheaper than configuration betrayal.

4 · Restore with the app attached · passed

Result: 35s recovery · deleted machine back in the running app · post-target writes correctly absent

Fired

A real oops at 23:51:34 — DELETE the k8s-worker-2 VM record, cascading to its interface and both IPs. Recovery target set four seconds earlier.

What recovery proved

Base backup + WAL replay rebuilt the database in 35 seconds. The deleted machine existed again; a table written after the target did not. Point-in-time means point-in-time.

The part restore stories skip

Living on the side-cluster isn't recovery. NetBox was repointed back to the canonical database and its hole healed by re-running populate — idempotently recreating exactly what was missing.

The blocker it exposed

Preflight found archiving silently OFF: CNPG refuses to write into a dead generation's prefix ("Expected empty archive") while every app stays green. Earlier rebuilds had run with no backups at all.

5 · Rebuild from git + blob · the thesis

Result: 8.5 min destroy-to-converged · 1 manual step · the database was BORN holding its data

Fired

make destroy, then a timed harness: up (88s) → bootstrap (140s) → platform (~142s) → six apps converged (141s).

Data survival, not rediscovery

The new cluster bootstrapped from the previous generation's archive. populate.sh — which creates anything it can't find — created nothing but the three new public IPs. Site, cluster, prefixes, VMs: already there.

The quiet proof

No token had to be minted: the API token in ~/.config/trk-k8s still matched the row restored from blob. Two independent survival paths agreeing across total infrastructure loss.

Three attempts, three instrument bugs

The harness measured a no-op and reported numbers; died before printing its own scorecard; then blocked on stdin that wasn't there. The instrument failed three times; the system under test failed zero.
