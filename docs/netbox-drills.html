The database that describes its own cluster

NetBox is an infrastructure inventory. Ours now holds 1 site, 1 cluster, 3 VMs, 4 prefixes, 6 IPs — the records of the very machines it runs on. That self-reference is the point: every drill below breaks something the database itself depends on, and "recovery" means those records come back.

Three loops keep it alive — traffic (you → Gateway → NetBox → Postgres), reconcile (git → Argo CD → everything), durability (Postgres → S3). Each drill attacks a different loop. Click through to see how the picture changes.

0 · Today — the healthy baseline

Diagram: everything quiet. pg-1 wears the PRIMARY badge; pods 2 and 3 are dashed because they don't exist yet.

Traffic loop

Cloudflare resolves netbox.k8s.kahng.dev to a node; Envoy terminates TLS and routes to the NetBox pod, which talks SQL through the pooler to whichever instance is primary.

Reconcile loop

Argo CD watches git and keeps six Applications Synced/Healthy. Nothing in the cluster is hand-applied; if you edit live state, selfHeal puts it back.

Durability loop

Every closed WAL segment ships to S3; a base backup lands every 6 hours. RPO = the currently-open segment, measured on two clouds.

Why the drills matter now

The database finally holds data you'd mind losing — the cluster's own records. Each drill kills one box above and asks: do those six IPs come back?

1 · Failover under load

Diagram: pg-1 goes red, the PRIMARY badge jumps to pg-2, pooler and NetBox run amber while the load chip hammers the front door.

You fire

kubectl -n postgres-cnpg delete pod pg-1 — while a load generator holds sustained requests against NetBox. I set up the load and the watchers first.

What happens

The CNPG operator notices the lost primary and promotes pg-2 — a centralized decision, unlike Patroni's self-managed election from 7.3. The pooler's rw endpoint follows the badge.

Watch

HTTP error rate on the load tool, kubectl cnpg status pg, and the pooler repointing. Expect a seconds-long window of failed writes, then silence.

Healthy again when

pg-1 rejoins as the replica (its PVC survived, so no re-clone needed), object counts are unchanged, and zero rows were lost — the pod died, the disk didn't.

2 · Migrations at replicaCount: 3

Diagram: pods 2 and 3 solidify — NetBox becomes three identical webs sharing one schema, and pg-1 runs amber while DDL takes locks.

You fire

A git commit: replicaCount: 3 plus a NetBox version bump in netbox.yaml. Argo CD does the rest — no kubectl.

What happens

The upgrade runs schema migrations while three pods serve. For a window, old code runs against new schema (or the reverse) — the classic many-apps-one-database problem, staged deliberately.

Watch

Migration locks in pg_stat_activity, rolling-update order, and whether any request 500s mid-roll. Migrations must apply exactly once, not once per pod.

Healthy again when

3/3 pods Ready on the new version, one clean migration history, no dropped requests you can't explain.

3 · Cache vs queue — kill Valkey

Diagram: Valkey goes red; NetBox web and worker run amber for different reasons — that difference is the whole lesson.

You fire

kubectl -n netbox delete pod netbox-valkey-primary-0. It's standalone by deliberate choice — no replica to save us.

What happens

Two very different losses from one pod: the cache is rebuildable — pages go slower until it re-warms. The queue is not — RQ jobs in flight (webhooks, reports) are simply gone.

Watch

Page latency (cache misses), worker logs (which jobs vanished), and whether NetBox errors or merely degrades. Enqueue a job before firing so there's something to lose.

Healthy again when

Valkey is back, latency normal, queues draining — and you can name exactly which work was lost. "Stateless" dependencies rarely are.

4 · Restore with the app attached

Diagram: a new pg-restore cluster appears, fed from S3 (the teal PITR path); the old cluster fades and NetBox's SQL line swings over to the restored database.

You fire

An "oops" first — delete a real VM record in NetBox and note the time. Then apply a recovery Cluster bootstrapped from barmanObjectStore with a recoveryTarget just before the oops.

What happens

CNPG pulls the nearest base backup from S3 and replays WAL up to the target — the 7.4 restore drill, but this time an application must come back with its data, not just a psql prompt.

Watch

Recovery logs on the new cluster, then NetBox after its DB host secret is repointed. The deleted record must exist again; anything written after the target must not.

Healthy again when

Counts match the pre-oops state, NetBox serves from the restored cluster, and the new cluster is archiving WAL to S3 again — restore that doesn't resume backups isn't done.

5 · Full rebuild from git + S3

Diagram: everything inside the cluster boundary dims. Only three boxes stay lit — GitHub, S3, and the laptop's secret files. That's the entire recovery kit.

You fire

make destroy, then the full bring-up: make up → bootstrap → platform, repoint the Cloudflare A record, run populate.sh.

What happens

Nodes, PVCs, pods — all gone. Git re-creates the platform (Argo CD converges six apps hands-off). S3 re-creates the data (recovery bootstrap). The laptop re-seeds the secrets, and populate.sh self-heals its own API token.

Watch

How little you type. Every manual step you catch yourself doing is a gap in git, the Makefile, or platform.sh — the drill's real output is that list.

Healthy again when

Six apps Synced/Healthy, NetBox reachable at its name, and the same counts — 1 site, 3 VMs, 4 prefixes, 6 IPs — on brand-new machines. Cluster as cattle, proven end to end.
