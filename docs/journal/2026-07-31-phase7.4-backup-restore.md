# 2026-07-31 — Phase 7.4 (part 3): the backup lab — the data survives

The first time in this entire project that a database could be destroyed
and brought back. Every phase until now proved *the cluster* survives
(drill 1 rebuild, drill 3 etcd restore, drill 4 node replacement) while
carefully keeping nothing worth losing. This is the other half.

## Infra: the bucket

S3 bucket `trk-k8s-pg-backups` + an inline policy on the existing
`k8s-node` IAM role (`infra/aws/main.go`, 2 resources, 14 unchanged).
Credentials reach barman via **IMDS on the node's own identity** —
`s3Credentials.inheritFromIAMRole: true`, no credential Secret anywhere,
the same path the EBS CSI driver uses (and the one that taught us the
hop-limit-3 lesson in Phase 4).

Two design corrections made while building it:

- **Fixed bucket name, not `BucketPrefix`.** A generated suffix can't be
  referenced from git — and the CRD has to name the bucket. Changed to
  `trk-k8s-pg-backups`.
- **Trade-off recorded for ADR 007:** instance-profile identity is
  NODE-scoped, so any pod on the node can reach the backup bucket. IRSA
  scopes per-ServiceAccount but needs an OIDC provider kubeadm doesn't
  create. Accepted for a lab with throwaway data; wrong for real
  backups.

Still open: the bucket lives in the same stack as the nodes with
`ForceDestroy`, so `pulumi destroy` reaps the backups too. Fine for a
same-session drill, **fatal for Phase 8's rebuild-with-state drill** —
whose entire premise is restoring into a cluster that didn't exist when
the backup was taken. Needs a separate lifecycle before then.

## Trap: the image variant, and a monitoring lie

Configured `spec.backup.barmanObjectStore`, got
`ContinuousArchiving: True` and `archived_count: 15` — and an **empty
bucket**.

Cause: CNPG splits its Postgres images by capability. I chose
`18.4-standard-trixie` to mirror our hand-built `postgres:18` — the one
variant that **dropped the barman-cloud binaries** (they're migrating
backups to the Barman Cloud Plugin). The operator's own default was
`18.4-system-trixie` all along; I overrode it for symmetry and paid.
Real error, once it surfaced:

    "barman-cloud-wal-archive": executable file not found in $PATH

**The dangerous part is what Postgres reported in the meantime.** With
no destination configured, CNPG's archive command exits 0, so
`pg_stat_archiver.archived_count` climbed to 15 for WAL that went
nowhere, and the cluster condition read "Continuous archiving is
working". Anyone alerting on `archived_count` or that condition would
have had a green dashboard and zero backups.

**Lesson: the only honest backup check is looking in the bucket.** After
the image swap, `failed_count` started climbing instead — archiving
failing loudly is strictly better than succeeding falsely.

(Fork in the road, decided: in-tree `barmanObjectStore` + `system` image
now; the Barman Cloud Plugin is the future direction but is v0.14.0,
released 2026-07-29, pre-1.0. Same shape as ADR 005's ingress-nginx
call, opposite answer — because in-tree isn't EOL, it's just no longer
the default path. Migration noted as a follow-up.)

Bonus observation: the image change triggered a **rolling image upgrade
on a live HA cluster** — replica first, then primary, no human steps. A
maintenance operation we never attempted by hand.

## The drill, designed to measure the recovery POINT

Not just "did data come back" but "how much was lost". Three markers:

| Marker | Where it lived | Predicted |
|---|---|---|
| A — before the base backup | inside the base backup | survives |
| B — after backup, WAL `…013` **archived** | replayed from S3 | survives |
| C — after that, WAL `…014` **never archived** | nowhere in S3 | **lost** |

Then `kubectl cnpg backup pg` (base backup: 4.2 MB gzipped `data.tar.gz`
+ `backup.info`), and recovery into **`pg-restored`** — a cluster that
did not exist when the backup was taken:

    bootstrap:
      recovery:
        backup:
          name: pg-20260731200155

(No `spec.backup` on the restore cluster — a second cluster pointed at
the same `destinationPath` would archive over the original's WAL.)

## Result: exactly one row lost

    marker C in ORIGINAL:   1
    marker C in RESTORED:   0
    total rows: 660 original vs 659 restored

Restored in **52 seconds**, and every drill marker from the whole
session came back — switchover, hard kill, apiserver fence — the entire
history of the day, reconstituted from an S3 bucket into a brand-new
cluster.

**This cluster's RPO, now measured rather than assumed: you lose the
currently-open WAL segment.** Not zero, not unbounded — a specific,
explainable amount. That's the number you want before an incident, not
during one. (`archive_timeout` bounds it by time; synchronous archiving
or streaming to a second site would shrink it further, at a cost.)

Also worth noting the operator's consistent instinct: recovery ran in a
dedicated `pg-restored-1-full-recovery-*` pod, same as `initdb` runs in
its own job pod. Bootstrap work is a separate, observable, disposable
unit — the opposite of our hand-built stack, where Patroni did bootstrap
inside the container that would later serve queries.
