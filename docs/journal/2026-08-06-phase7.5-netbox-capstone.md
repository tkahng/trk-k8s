# 2026-08-06 — Phase 7.5: NetBox on CNPG, and an error message that lied

The capstone deployed. `https://netbox.k8s.kahng.dev:30443` returns 200 with a
verified Let's Encrypt wildcard cert, 198 tables in the CNPG-managed `netbox`
database, web pod and RQ worker both Running, all six ArgoCD apps
Synced/Healthy.

The request path is the whole project in one line: Cloudflare → Azure public
IP → NSG rule scoped to the admin address → hostNetwork Envoy on 30443 →
Cilium's Gateway API → the chart's native HTTPRoute → eBPF service
translation with no kube-proxy → Django pod → pgbouncer → CNPG primary →
`netbox` database.

## The build

- **Application via the Helm-source pattern** (second use, after
  cnpg-operator): ArgoCD renders chart 8.3.46 from
  `charts.netbox.oss.netboxlabs.com` directly, `valuesObject` inline. No
  vendoring.
- **A second database inside the existing `pg` cluster**, not a second
  Cluster CR — another 2-instance cluster would double Postgres memory on
  three 4 GiB nodes for no lesson. Declared with CNPG's `Database` CRD plus
  a `managed.roles` entry, so role and database are reconciled rather than
  created by hand with psql. The shared blast radius is deliberate: a
  failover of `pg` moves NetBox with it, which is exactly what makes drill 1
  meaningful.
- **The same DB password written into two namespaces** — `postgres-cnpg` so
  CNPG's role reconciler can set it, `netbox` so the app can use it. Secrets
  don't cross namespaces and one credential doesn't justify a replication
  controller.
- **First real `requests`/`limits`** in this project. Three 4 GiB nodes
  already run the platform stack at ~40% plus two CNPG instances.
- **Native Gateway API in the chart** (`httpRoute.enabled`) — no Ingress, no
  hand-written route. The Phase 6.5 promise cashed exactly as predicted: a
  new app is HTTPRoute + DNS, TLS already handled by the Gateway's wildcard.

## The GitOps-with-Helm trap (found by reading, not by failing)

The chart generates `secret_key` and `api_token_peppers` using Helm's
`lookup` to preserve existing values across upgrades. **`lookup` returns
EMPTY under `helm template`, which is how ArgoCD renders.** Left alone the
chart would mint a fresh `secret_key` on every sync — invalidating sessions
and producing permanent diff churn that would present as a mystery.

Fix: supply everything via `existingSecret` / `superuser.existingSecret`,
created by platform.sh from local files (the 7.x pattern). Worth
generalising: **any chart that self-generates secrets is suspect under
GitOps**, because the mechanism it uses to be idempotent is the one thing
template-only rendering takes away.

## The error message that lied — the day's real lesson

NetBox crash-looped printing:

    ⏳ Waiting on DB... (27s / 30s)
    ❌ Waited 30s or more for the DB to become ready.

So I tested the database. Five ways:

1. Pooler config — `* = host=pg-rw`, a wildcard, serves any database ✓
2. `netbox` role exists and can log in ✓
3. Cross-namespace DNS and TCP from the `netbox` namespace ✓
4. psql through the pooler as `netbox` to `netbox` ✓
5. psql with NetBox's **exact** connection options, including
   `sslmode=prefer target_session_attrs=read-write` ✓

Every single one passed. **The database was never the problem.**

The actual complaint was one easily-missed line repeating *above* each wait:

      python /opt/netbox/netbox/generate_secret_key.py

`SECRET_KEY` was too short. NetBox requires **≥50 characters**, and
`openssl rand -base64 36` produces exactly **48** — two short. Fixed that,
and the same 48-char generator failed again on a different field:

    ImproperlyConfigured: Invalid pepper 1: Pepper must be at least 50
    characters in length.

Two 50-character minimums, one bad generator, both surfacing as a fake
database timeout.

**The generalisable lesson: when every test of the thing the error names
comes back clean, stop testing that thing.** And read the *repeating* line,
not the *final* one — the loop message was noise, the suggestion above it was
signal. The chart offers `dbWaitDebug: true` to print the real traceback;
that hint is now a comment in the Application so the next person skips the
hour.

(There is a family resemblance to 7.4's `archived_count` lie — a system
reporting confidently about the wrong thing. There the counter said success
while the bucket was empty; here the error named a component that was
entirely healthy. Both cost an hour, both were cracked by checking the thing
itself rather than the thing's self-report.)

## Two smaller finds

- **CNPG `Database` and `managed.roles` have no ordering guarantee.** The
  Database CR failed with `role "netbox" does not exist` because it ran
  before the role was reconciled. It retried and converged — self-healing,
  but worth knowing the race exists.
- **The chart's default Valkey is a primary plus THREE replicas** — four
  Redis pods for a lab cache. Set `architecture: standalone`. Replication
  buys nothing here, and one pod makes drill 3 (kill the cache/queue)
  cleaner to observe.
