# 2026-07-26 — Phase 7.3 (part 1): Patroni bootstrap, and the four traps between "applied" and "streaming"

Built and deployed the two-member Patroni cluster (ADR 006: k8s-API DCS,
custom image). The manifests were "correct" by every document we read —
and the bootstrap still failed four different ways, each one a real
lesson that no amount of reading had surfaced. Ended the session
streaming: primary + async replica, verified end-to-end through
pgbouncer.

## Trap 1 — the scope-name collision (endpoints controller vs Patroni)

Symptom: postgres-1 bootstrapped (`initialized a new cluster`), then
10 seconds later `Could not take out TTL lock` → `Demoting self
(immediate-nolock)` — a self-fence right after a successful initdb,
repeating forever. No ERROR line anywhere.

Dead ends eliminated: RBAC (`kubectl auth can-i` as the SA: yes to
everything), pod IP env expansion (member annotations showed real IPs),
API writability (created a test Endpoints with subsets AS the SA: fine —
and Patroni had already created `postgres-config` and patched pod labels).

The answer was in the source (`dcs/kubernetes.py`):

    def leader_path(self):
        return super().leader_path[:-7 if self._api.use_endpoints else None]

**In use_endpoints mode the leader object is the Endpoints named after
the scope ALONE** — `postgres`, not `postgres-leader`; only -config/
-failover/-sync keep suffixes. And Endpoints/postgres already existed:
it belonged to our headless governing Service `postgres` (7.1), whose
selector makes the endpoints controller its owner. Patroni lost the CAS
to the controller every cycle — the write "succeeded" and was reverted
before the next read, hence no exception, no lock, no leader.

Fix: the scope name doubles as the leader Service name, so nothing else
may claim it. Headless Service renamed `postgres-pods` (StatefulSet
`serviceName` is immutable → delete + recreate); `postgres` became the
selector-less leader Service; pgbouncer upstream is now
`postgres.postgres.svc`. This is why Zalando clusters name the primary
Service after the cluster itself — a convention that looked cosmetic
until it cost us an evening.

## Trap 2 — the OrderedReady deadlock

After the rename cutover, a new circle: the DCS initialize key pointed
at the data on postgres-1's PVC (it had bootstrapped during the trap-1
mess), but OrderedReady wouldn't create postgres-1 until postgres-0 was
Ready — and postgres-0, with an empty volume and an already-initialized
cluster, sat `waiting for leader to bootstrap`. Ordinal 0 waiting for
ordinal 1's data; ordinal 1 waiting for ordinal 0's readiness.

Not an artifact of our race: lose member 0's volume after any failover
and the same deadlock forms in production.

Fix: `podManagementPolicy: Parallel`. Patroni already has its own
bootstrap ordering — the DCS initialize-key CAS decides who initdbs —
and the StatefulSet must not impose a second one on top. (The k8s docs
frame OrderedReady as the safe default; for a system with its own
coordinator it's the *unsafe* one.)

Operational footnote: the wipe itself (PVCs + DCS endpoints) raced
ArgoCD selfHeal recreating the StatefulSet — pods pinned the
Terminating PVCs. Had to pause automated sync (`syncPolicy.automated:
null`), wipe in order, restore the policy from git. selfHeal is the
GitOps dividend and it fights you exactly when you're doing surgery.

## Trap 3 — the invisible scope label

Clean-slate parallel bootstrap: postgres-1 won the initialize race,
took the lease (`transitions: 0`), wrote its own IP+targetRef into the
Endpoints subsets — election fully working. postgres-0 then failed
`trying to bootstrap from leader` → `failed` in ~1 millisecond, every
10 seconds, no reason given, wiping its data dir each round.

1ms is too fast to be a network attempt. Manual `pg_basebackup` from
inside postgres-0 to the leader: **rc=0** — network, SCRAM, pg_hba,
replicator user all fine. /tmp empty: Patroni never even wrote its
pgpass. So the failure was before the method launched. Source again
(`postgresql/bootstrap.py` create_replica): if the clone member has no
`conn_url`, basebackup is filtered out of the method list — the loop
runs zero iterations and returns failure without logging anything.

Why no conn_url? `dcs/kubernetes.py:756`:

    self._labels[config.get('scope_label', 'cluster-name')] = config['scope']

**Patroni's member-pod selector is `kubernetes.labels` PLUS
`cluster-name=<scope>`, appended automatically — but Patroni only ever
STAMPS the role label on pods, never the scope label.** Our template
carried only `app: postgres`, so the member watch matched zero pods:
elections work (the lock write needs no member list), self-status
annotations work (written by name), but cross-member discovery is
blind — a replica sees a leader *record* with no member behind it.

Fix: `cluster-name: postgres` in the pod template labels. One line.

## Trap 4 — the trailing newline (one byte, everywhere it matters)

With discovery fixed, pg_basebackup finally *ran* — and died with
`password authentication failed for user "replicator"`. Yet a manual
basebackup using the container's env had succeeded an hour earlier.
That asymmetry was the tell: **env-based auth worked, pgpass-file auth
failed**.

`openssl rand -base64 24 > file` writes a trailing newline;
`--from-file` / raw `base64 <file` preserved it into the Secret
(33 bytes, 32 without newlines — checked with `wc -c`, never printing
the value). The env var carries the newline, so Patroni *created*
`replicator` with `password\n`. But pgpass is line-oriented: the
newline terminates the entry, so pg_basebackup sends `password`. The
database held one value; the wire carried another; both were "the
secret".

Fix, no re-bootstrap needed: `ALTER ROLE replicator PASSWORD` to the
stripped value (matching what pgpass sends), patch the Secret, strip
the local file, and platform.sh now generates with `tr -d '\n'` and
creates via `--from-literal="$(cat file)"` (command substitution strips
trailing newlines; `--from-file` faithfully keeps them).

Footnote from the same minutes: pgbouncer kept reporting
`client_login_timeout (server down)` after everything else was green —
its pods predated the ini flip and still pointed at the dead
`postgres-0.postgres.…` DNS name. Inline ConfigMap edits don't restart
consumers (the documented trade from 7.2 — you choose when to roll):
`kubectl rollout restart deploy pgbouncer` completed the migration.

## The debugging pattern that actually worked

Logs said nothing three times. What broke each case open:

1. **Reproduce the exact write as the exact identity** — `kubectl
   --as=system:serviceaccount:...` creating a test Endpoints separated
   "API refuses" from "Patroni refuses".
2. **Reproduce the exact operation by hand in the pod** — manual
   pg_basebackup with the container's own env proved the entire
   replication path and cornered the bug into Patroni's preflight; the
   same test's *success* was what later exposed the env-vs-pgpass split.
3. **Read the source shipped in the image** — the image IS the running
   code; `docker run --entrypoint sh` + grep found three of the four
   answers (`[:-7]`, the empty method list, the appended scope label)
   faster than any documentation.
4. **Compare byte counts, not values** — `wc -c` vs `tr -d '\n' | wc -c`
   diagnosed the secret without ever printing it.
