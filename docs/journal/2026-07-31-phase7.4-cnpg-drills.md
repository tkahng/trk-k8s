# 2026-07-31 — Phase 7.4 (part 2): the drills, re-run against CNPG

The 7.3 drill card, replayed against the operator. Same markers-through-
the-pooler technique, same triggers, same measurements — so the numbers
compare 1:1 with the hand-built Patroni stack. Three drills, and the
third produced a result I did not expect.

Bring-up first: **third consecutive hands-off resume**, and the
`ServerSideApply` fix held from birth — CRDs applied on first sync, zero
operator crash-loops, zero manual kicks. Yesterday's four-costume
cascade is genuinely gone. CNPG bootstrap: **78s** from CR to 2 healthy
instances.

## Drill 1 — planned switchover

`kubectl cnpg promote pg pg-2`. Both markers survived, ex-primary
rejoined streaming, timeline 1→2.

| | Hand-built (Patroni) | CNPG |
|---|---|---|
| Role swap | ~10s | **1s** |
| App writes restored | **~3 min** (manual per-pod `RECONNECT`) | **2s**, automatic |
| Command | `patronictl -c /etc/patroni/patroni.yml switchover postgres --leader … --candidate … --force` | `kubectl cnpg promote pg pg-2` |

**The pooler gap is closed.** Same pgbouncer software as ours — the
difference is that ONE controller owns both the promotion and the pool,
so there is no coordination gap to fall into. 7.3's find-of-the-day
becomes a non-issue by architecture, not by better components.

## Setup accident — cordon IS a failover trigger

Cordoning the primary's node (my 7.3 technique for blocking pod
resurrection) caused CNPG to **immediately and gracefully switch the
primary away**. The operator ships `drainTaints` including
`node.kubernetes.io/unschedulable` — exactly the taint `kubectl cordon`
applies — and reads it as "this node is leaving, evacuate the primary."

In 7.3 a cordon was inert; Patroni never noticed. Here node maintenance
is **safe by default**: the failover happens on your terms, before the
drain, instead of as an unplanned event mid-drain. Operational knowledge
we didn't have and wouldn't have thought to build. It also invalidated
my drill setup — the tool was too careful for the test.

## Drill 2 — hard kill of the primary (healthy node)

Forced pod deletion, no cordon. From the cluster's own event record:

    02:14:13  pod force-deleted
    02:14:14  readiness probe fails (HTTP 500)
    02:14:15  "Current primary isn't healthy, initiating a failover"   <- 2s
    02:14:15  "Failing over from pg-1 to pg-2"
    02:14:36  first successful app write through the pooler            <- 23s

Two findings:

- **Detection in 2s, not 30.** Patroni infers death from *absence* —
  waiting out the 30s lease TTL. CNPG **actively health-checks** every
  instance, so a failed readiness probe is direct evidence. Same job,
  opposite epistemology, and most of the 30s→2s difference.
- **It made the opposite DECISION from our stack.** In 7.3 this exact
  drill was a non-event: the StatefulSet controller resurrected the pod
  faster than Patroni's TTL could expire — two systems, unaware of each
  other, faster one wins by accident. CNPG owns both pod lifecycle and
  failover, so it weighed them and chose: promote the healthy replica
  now, rebuild the dead one as a replica after. Not a race — a judgment.

(Method note: my first stopwatch measured from when I armed it, not from
the kill — contaminated by the wait for a human trigger. The event
record gave the honest numbers. Lesson: for human-triggered drills,
timestamp from the cluster's own events, not the observer's clock.)

## Drill 3 — the apiserver fence: CNPG DOES NOT FENCE

The headline. Same trigger as 7.3 (`mv` the kube-apiserver manifest out
on cp-1), same SSH+crictl periscopes because kubectl dies with the API.
Apiserver down **02:40:29 → 02:47:26, ~7 minutes**.

Result: **nothing happened to the database.**

    probe_writes | first    | last     | biggest_gap_seconds
    423          | 02:24:58 | 02:47:45 | 4

423 probe writes across the whole session at a 3s cadence, and the
largest gap between consecutive successful writes was **4 seconds** —
i.e. normal jitter. Writes never stopped. Primary never changed.
Timeline stayed 4. Zero pod restarts. `hello=200` unbroken (the drill-3
control). Cluster returned to `healthy` the moment the API came back,
with nothing to recover.

Compare 7.3: Patroni self-fenced within its 30s TTL, demoting a
perfectly healthy database, and writes failed read-only for the entire
outage plus a ~3min pooler tail.

**Was CNPG merely oblivious? No — it noticed and chose.** The primary's
instance manager logged **128 errors** during the outage, all
`Failed to watch` from its API cache reflector. It knew the control
plane was gone, said so continuously, and kept serving Postgres.

### Why the architectures differ (the real lesson)

- **Patroni: leadership IS a lease.** Any member can try to promote
  itself — promotion is a distributed decision. So a leader that cannot
  renew its lease *must* demote: it can no longer prove no rival has
  taken over. Fencing is structural, not configurable.
- **CNPG: promotion is centralized in the OPERATOR.** Instances never
  promote themselves. If the API is unreachable, the operator can't act
  either — so **nobody can promote**, and the existing primary can
  safely keep serving. Verified: the replica logged zero
  promote/primary mentions and the timeline never advanced.

Neither is "safer" in the abstract; they optimize for different failure
modes. Patroni's design is safer where a partitioned member might act
unilaterally. CNPG's is safer where control-plane maintenance would
otherwise take your database down with it — and it achieves that by
removing unilateral action from instances entirely.

**This substantially revises ADR 006's premise.** We bought
"control-plane outage = database write outage" as the price of the
k8s-API DCS. That price is a property of *Patroni's* leadership model,
not of using the Kubernetes API for consensus. Same API, same coupling
on paper, opposite behavior in practice.

(Honest scope: the outage probe wrote via the container's local socket,
so it proves the DATABASE never stopped accepting writes. The pooler
path was necessarily unaffected too — no failover meant pg-rw's target
never moved and pgbouncer's established connections stayed valid — but
that leg was inferred, not directly probed.)
