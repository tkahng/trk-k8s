# 2026-07-18 — Phase 7.2: PgBouncer, and why Postgres needs one

Second step of the progression: a pooler in front of postgres-0,
hand-written `pgbouncer.ini` (the edoburu image would happily generate
config from env vars — declined on purpose; writing the ini is the
lesson). Image: `edoburu/pgbouncer:v1.25.2-p0` — the community standard;
the official project ships no image and Bitnami's went behind a paywall
in 2025.

## The why, in one demo

Postgres forks one OS process per connection; `max_connections`
(default 100) is a hard wall, and app platforms open many mostly-idle
connections. With `pool_mode = transaction` and a deliberately tiny
`default_pool_size = 2`:

    clients connected: 5
    real backends running pg_sleep: 2
    all 5 finished

Five concurrent clients, two real server processes, zero failures — the
other three queued inside pgbouncer and ran in waves. Multiplexing, not
magic: a server connection is borrowed per transaction and returned at
commit, so idle clients hold nothing. The trade: session state (SET,
LISTEN, advisory locks) dies at transaction end; protocol-level prepared
statements need `max_prepared_statements` (pgbouncer ≥1.21).

## Deliberate contrasts (the k8s lesson riding along)

- **Deployment vs StatefulSet**: pgbouncer holds no state → random pod
  names, no PVC, reschedules anywhere, `replicas: 2` costs nothing.
  postgres-0 got none of those freedoms. Same phase, both kinds, side
  by side.
- **VIP Service vs headless**: clients shouldn't care which pgbouncer
  answers → normal Service. Postgres needs per-instance identity →
  headless. Apps connect to `pgbouncer.postgres.svc`, never postgres-0;
  that indirection is what keeps app config stable when 7.3 adds
  failover.

## Auth plumbing worth remembering

Clients SCRAM to pgbouncer; pgbouncer SCRAMs upstream. The auth_file
holds the plaintext password to make both ends work — rendered by an
init container into a tmpfs (`emptyDir.medium: Memory`) from the same
`postgres-credentials` Secret postgres uses. Nothing new in git, nothing
on disk.

## Gotchas

- **Pool math multiplies by replica count.** The service spread clients
  across 2 pgbouncer pods, each with its own pool of 2 → up to 4 real
  backends, and the "5 clients / 2 backends" demo only reads clean when
  aimed at a single pod. Sizing rule: real ceiling = pool_size × pooler
  replicas.
- Admin console (`psql -d pgbouncer`, `SHOW POOLS`) reports per-pod
  state only — there is no fleet view; that's what operators/metrics
  exporters add later.
- Counting backends from psql-inside-shell-inside-exec: `LIKE
  '%pg[_]sleep%' ESCAPE '['` mangled through three quoting layers;
  exact-match `WHERE query = 'SELECT pg_sleep(3)'` is the reliable form.
