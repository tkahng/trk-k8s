# 2026-07-29 — Phase 7.4 (part 1): CNPG bring-up — one root cause, four costumes

Started the operator phase: CloudNativePG 1.30.0 installed via a new
ArgoCD pattern (Application sourcing a public Helm chart — no vendoring,
version pinned), plus a Cluster + Pooler CRD in `apps/postgres-cnpg/`,
deployed alongside the hand-built stack as its control group. The
bring-up itself was the day's drill: one root cause produced four
distinct failures, each wearing a different costume.

## The cascade

1. **Root cause: CNPG's Cluster/Pooler CRDs are megabyte-scale.**
   Client-side apply writes the whole object into the
   `last-applied-configuration` annotation → died on the 256KiB
   annotation cap. 9 of 11 CRDs landed; the two that didn't were
   exactly the two that matter. Fix: `ServerSideApply=true` sync option
   (SSA tracks field ownership in the apiserver; no annotation, no cap).
2. **Costume #1:** operator CrashLoopBackOff ×12 on
   `no matches for kind "Cluster"` — an operator that can't find its
   own CRD looks like a broken operator, not a broken apply.
3. **Costume #2: the git fix did nothing.** Application manifests are
   applied imperatively by platform.sh and NOTHING watches them —
   editing `cluster/gitops/*.yaml` in git changes no live object. The
   asymmetry noted in the ArgoCD walkthrough ("ArgoCD deploys the apps
   from git, but nothing deploys the Applications") bit in real time.
   Fix was a hand `kubectl apply` — the exact indignity GitOps exists
   to remove. **App-of-apps graduates from loose end to necessity,
   with a dated incident attached.**
4. **Costume #3: even applied, nothing happened.** ArgoCD's automated
   sync had exhausted its attempts on that revision and will not
   re-attempt it — a syncPolicy change doesn't count as new. selfHeal
   reverts drift; it does not retry defeats. A sync must be requested
   explicitly (`kubectl patch application … '{"operation":{"sync":…}}'`
   or the UI button).
5. **Costume #4:** with the operator finally starting, the Cluster CR
   still bounced — `failed calling webhook … no route to host`: the
   admission webhook Service had no ready endpoints while the operator
   crash-looped. Self-cleared on the app's next retry once the operator
   stayed up. (Admission webhooks move config errors from runtime to
   apply time — the price is the webhook being load-bearing for the CR
   at all.)

The postgres-cnpg app's `retry` block (designed for the CRD race)
absorbed costumes 3-4 downstream without human help. The operator app
had no retry block — it needed the manual kick. Asymmetric on purpose?
No: oversight. Symmetry noted for the follow-up.

## Then it worked — the numbers

From the Cluster CR landing to a healthy 2-instance cluster: **76
seconds** — pg-1 initdb'd, pg-2 cloned ~40s behind it, two pooler pods
serving. All four Applications Synced/Healthy. Smoke test: generated
`app` credentials → pg-pooler-rw → primary, first try.

## The inventory (30 lines of CRD manufactured…)

- 4 Services (pg-rw / pg-ro / pg-r / pg-pooler-rw), operator-maintained
- 5 Secrets — including a full internal **PKI**: CA, server cert,
  **mTLS replication client cert** (there is no replication password to
  newline-mangle: 7.3 trap 4 isn't fixed, its substrate is removed),
  pooler cert; plus `pg-app` with 11 keys incl. ready-made URIs
- **PodDisruptionBudget on the primary** — pre-armor against drill 2's
  drain choreography; we never thought to build one
- Per-component ServiceAccounts/Roles; per-instance PVCs (no
  volumeClaimTemplates — no StatefulSet at all, pods managed directly:
  7.3 trap 2's whole category deleted)
- Pods labeled `cnpg.io/instanceRole: primary|replica`

The honest measure: the operator didn't just automate what we built in
7.1-7.3 — it encoded operational knowledge (TLS everywhere, disruption
budgets) we hadn't acquired yet.
