# 2026-07-18 — Phase 6.5: Cilium Gateway API, kube-proxy retired on the way

Migrated the edge from ingress-nginx (EOL upstream) to Cilium's Gateway
API implementation. The headline lesson: what looked like one migration
was two — Cilium's Gateway API **requires** kube-proxy replacement, so the
"replace kube-proxy someday" lab (deliberately deferred in the cilium
values since Phase 3) became today's prerequisite.

## Lab A — kube-proxy replacement (live, on a running cluster)

Order matters when swapping the service plane under a live cluster:

1. `helm upgrade` cilium with `kubeProxyReplacement=true` +
   `k8sServiceHost=10.0.1.10` — Cilium's eBPF takes over service
   translation while kube-proxy's iptables rules still exist (they
   coexist; existing connections may break, new ones are fine)
2. verify `cilium-dbg status` → `KubeProxyReplacement: True`
3. only then delete `ds/kube-proxy` + `cm/kube-proxy` and flush
   `KUBE-*` iptables rules on every node

Why `k8sServiceHost` must be explicit: the in-cluster `kubernetes`
Service VIP that agents normally bootstrap through *was kube-proxy's
job*. Chicken-and-egg — so the real API server address is passed from
the inventory (provider-specific → a bootstrap.sh `--set`, not
values.yaml).

Verified after: in-cluster DNS, ClusterIP, external NodePort, ArgoCD all
fine with zero kube-proxy pods. kubeadm init now runs
`--skip-phases=addon/kube-proxy` for rebuild parity.

Gotcha (own goal): `kubectl delete ds kube-proxy cm/kube-proxy` errors —
can't mix bare and resource/name forms; the delete silently didn't
happen while the iptables flush did. Kube-proxy would have re-created
its rules. Caught because the delete's error output was actually read.

## Lab B — Gateway API

- CRDs first (v1.4.1 standard channel), *then* enable — Cilium only
  registers its controller if the CRDs exist at agent start. Encoded in
  bootstrap.sh before the cilium helm install.
- `gatewayAPI.enabled=true` + `hostNetwork.enabled=true` in cilium
  values; `config.gatewayAPI.enabled=true` in cert-manager values;
  restart operator+agents+cert-manager; `GatewayClass cilium` → Accepted.

**hostNetwork mode is the find of the day:** Envoy binds listener ports
directly on every node — the Gateway-API-era answer to ADR 003 (no cloud
LB, no MetalLB, portable). We kept nginx's exact ports 30080/30443, so
the SG rules, the Cloudflare record, and every URL survived unchanged.

## The migration itself (zero-downtime-ish)

1. Gateway `main` in its own `gateway` ns on TEMP ports 30081/30444
   (nginx still owned the real ones), wildcard `*.k8s.kahng.dev`
   listeners, `cert-manager.io/cluster-issuer` annotation → gateway-shim
   issued ONE wildcard cert via DNS-01 in ~90s
2. hello: HTTPRoute added *alongside* the Ingress, pushed, ArgoCD synced
3. verified on temp ports from a node (SG self-rule) — 200 over verified
   TLS before touching anything user-facing
4. cutover: uninstall ingress-nginx → flip listener ports → external 200
   in seconds
5. removed Ingress from git; ArgoCD `prune` deleted the live object and
   its ingress-shim Certificate followed (ownerRef GC); one orphaned
   `hello-tls` secret swept by hand

The teachable contrast: the app's HTTPRoute has **no TLS config at all**
— hostname + backend, nothing else. Cert and ports are infra's problem
now (the Gateway), which is precisely the role separation Gateway API
was designed around. whoami now echoes `X-Envoy-External-Address` —
the proxy in the path is visibly Envoy.

## Quirks & notes

- hostNetwork Gateways report `PROGRAMMED=False ("waiting for address")`
  forever — no LB Service to copy an address from. Serving fine; verify
  with curl, not status. Noted in runbook 05.
- ArgoCD "Synced/Healthy" can be a stale revision (3-min poll) — force a
  refresh with the `argocd.argoproj.io/refresh` annotation before
  concluding a push didn't work.
- One wildcard cert at the Gateway means new apps are: HTTPRoute + DNS.
  Nothing per-app to issue. Phase 7's capstone gets HTTPS for free.
