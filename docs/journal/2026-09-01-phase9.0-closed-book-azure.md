# 2026-09-01 → 09-03 — Phase 9.0, closed book on Azure: what memory actually produced

Three evenings, one fresh kubeadm cluster built by hand with the repo
closed, stopped one step short of the finish line by a driver that
changed underneath us. Ended early by choice: the credits die Sept 4 and
the Azure CSI detour was eating the timebox, so 9.0 resumes on Hetzner.
This entry records the honest result — the recall score and two findings
the answer key didn't know about.

## The rule, and how it bent

Closed book was defined as "no `cluster/`, no runbooks, no journals."
Within the first twenty minutes it had to be refined: **the repo is
closed, the public internet is open.** The test is whether you know
*what* to do and *why*, not whether you've memorized apt syntax — and
working from the Kubernetes docs is exactly what building from scratch
looks like at a new job. Hints were asked for explicitly and logged; the
log is the recall score.

## Mechanics that cost time

- **Paste path truncation.** Multi-line commands with `\` continuations
  and any line past ~100 chars got clipped on the way into the terminal:
  `ca-certificates curl gpg` became `ca-`, the pkgs.k8s.io URL lost its
  tail (hence a 403), and a half-written `kubernetes.list` then broke
  every `apt` call until removed. This is why the scripts run over `ssh`
  with `set -e` rather than being pasted. Fix used: one command per line,
  long lines split into download-then-use.
- **`export KUBECONFIG` is per-shell.** Helm's `localhost:8080` error is
  the tell for "no kubeconfig at all." The Makefile passes `--kubeconfig`
  explicitly for this reason.
- **Apply order.** The StorageClass was written but never applied before
  the PVC; the claim sat with an empty class. Retroactive default
  assignment (1.28+) fixed it once the class existed — but "class before
  claims" is the habit.

## Finding 1 — azuredisk-csi-driver chart 1.34.5 breaks `platform.sh`

The controller pod came up `5/6`, the `azuredisk` container in
CrashLoopBackOff: *"no cloud config provided … /etc/kubernetes/azure.json:
no such file."* The chart's `controller.allowEmptyCloudConfig` now
defaults to `false` (the node plugin's is still `true`). The August
install (journal 2026-08-05: *"needed no cloud-config plumbing"*) worked
on an older chart. `platform.sh` installs the chart unpinned, so **the
repo's own Azure storage path would crash on its next rebuild.**

## Finding 2 — `allowEmptyCloudConfig=true` only moves the crash

Flipping the flag got the controller to `6/6`. First `CreateVolume`:
`rg() location()` empty in the log, then a nil-pointer panic in
`CreateManagedDisk` — surfacing to the PVC as `rpc error … EOF`. The
startup log says it plainly: *"disable UseInstanceMetadata for
controller."* Driver v1.34.5 no longer lets the controller discover
subscription/RG/location via IMDS; it demands an explicit config. The
managed-identity *design* still holds — no credential in the cluster —
but the auto-discovery is gone.

The fix the driver asks for on its first log line: a Secret
`kube-system/azure-cloud-provider`, key `cloud-config`, containing an
`azure.json` with `tenantId`, `subscriptionId`, `resourceGroup`,
`location`, `useManagedIdentityExtension: true` and
`userAssignedIdentityID` (the identity's client ID). IDs only, no
secret. Every value is available from Pulumi outputs, which is where
`platform.sh` should generate it from. Staged but not applied — the
session was stopped here.

## The Hetzner question, asked at the right layer

While the PVC sat Pending: "how about when I want to run on Hetzner?"
Storage is the *one* place the cloud leaks through the seam, and the
answer is worth recording: different driver (`hcloud-csi`,
`csi.hetzner.cloud`), a StorageClass differing only in the provisioner
line, 10Gi minimum volumes — and, for the first time, **a cloud
credential inside the cluster**, because Hetzner has no instance-identity
mechanism; the driver needs an API token in a Secret. Everything above
the class (PVC, pod, every CNPG manifest) moves untouched. Static
provisioning was considered and rejected: it makes disks precious again,
and this repo's persistence story is git + WAL archive, not surviving
disks.
