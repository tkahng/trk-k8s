# ADR 007 — CloudNativePG as the Postgres platform; and what 7.3 got wrong

Date: 2026-07-31. Status: accepted (Phase 7.4).

## Context

Phases 7.1–7.3 built Postgres HA by hand: StatefulSet, PgBouncer,
Patroni on the Kubernetes-API DCS, with a custom image and a
hand-written `patroni.yml` (ADR 006). That work produced a concrete
list of things we had to discover, fix, or work around — the rubric
this ADR judges an operator against. Phase 7.4 ran CloudNativePG 1.30.0
alongside the hand-built stack and replayed the same drill card.

## Decision

**CloudNativePG is the Postgres platform for this project.** The
hand-built stack in `apps/postgres` stays in the repo as the reference
implementation — it is what makes the operator legible — but it is no
longer the thing we would build on.

**Zalando's postgres-operator is dropped from the plan** (was PLAN.md
7.4's second candidate). Its value was "see your Patroni architecture
generated by machinery", and we now have that comparison in more detail
than an install would give: we built the Patroni architecture ourselves
and measured it against a non-Patroni operator on identical drills. A
third data point on the same axis doesn't earn its cost.

## The rubric, scored

| 7.3 finding | CNPG's answer |
|---|---|
| OrderedReady deadlock → `podManagementPolicy: Parallel` | No StatefulSet at all; the operator manages pods directly and owns bootstrap ordering |
| Scope-name collision (leader Service must be the scope name) | Operator owns and names `pg-rw`/`pg-ro`/`pg-r`; no convention to violate |
| Invisible `cluster-name` label breaking member discovery | Operator stamps every label its own watches need |
| Trailing newline splitting env-auth from pgpass-auth | Credentials generated, never hand-carried; replication uses **mTLS client certs**, so the failure mode's substrate is removed, not patched |
| File-vs-DCS config drift (`bootstrap.dcs` read once, then editable only via `patronictl`) | The CRD is the single source, reconciled continuously |
| **The pooler gap** — DB failed over at 08:26, app writes recovered 08:29, needing manual per-pod `RECONNECT` | `Pooler` CRD: same pgbouncer, but one controller owns promotion *and* pool → **2s**, automatic |
| No backup story at all | WAL archiving + base backups + PITR; restore into a cluster that didn't exist, RPO measured |

It also brought operational knowledge we had not acquired: a
PodDisruptionBudget on the primary, TLS everywhere by default, and
graceful primary evacuation when a node is cordoned (`drainTaints`) —
node maintenance is safe by default, where our stack would have taken
an unplanned failover mid-drain.

Measured, same drills, same markers-through-the-pooler method:

| Drill | Hand-built (Patroni) | CNPG |
|---|---|---|
| Planned switchover | ~10s + ~3min manual pooler recovery | 1s; pooler at 2s |
| Kill primary (healthy node) | no failover — StatefulSet won the race | promote in 2s, writes at 23s |
| Detection mechanism | lease TTL expiry (30s), infers death from absence | active health probe (2s), observes it |
| Apiserver down ~7 min | **self-fenced; full write outage** | **zero impact; kept serving** |
| Restore after data loss | impossible | 52s, RPO = one open WAL segment |

## The ADR 006 revision (the important part)

ADR 006 recorded that choosing the Kubernetes API as the DCS bought a
coupling: *control-plane outage ⇒ database write outage*, the deliberate
exception to drill 3's "control plane down ≠ outage". Phase 7.3's fence
drill confirmed it.

**That premise was wrong, and Phase 7.4 disproves it.** With the
apiserver down ~7 minutes, CNPG's primary kept serving: 423 probe
writes, largest gap 4 seconds, no promotion, timeline unchanged. It was
not oblivious — its instance manager logged 128 `Failed to watch`
errors throughout. It knew, and chose.

The difference is the leadership model, not the DCS:

- **Patroni: leadership IS a renewable lease, and any member may promote
  itself.** Promotion is a distributed decision, so a leader that cannot
  renew must demote — it can no longer prove no rival took over.
  Fencing is structural.
- **CNPG: promotion is centralized in the operator.** Instances never
  self-promote. If the API is unreachable the operator cannot act
  either, so *nobody* can promote — and the incumbent primary is safe to
  keep serving.

Neither is safer in the abstract; they optimize different failure modes.
Patroni's protects against a partitioned member acting unilaterally.
CNPG's protects against control-plane maintenance taking the database
with it, and earns that by removing unilateral action entirely.

**Corrected statement of the trade:** using the Kubernetes API for
consensus does not by itself couple database availability to control
plane availability. *A self-promoting leader model does.*

## Consequences

- **Image variant is load-bearing.** `standard` images dropped the
  barman-cloud binaries; in-tree `barmanObjectStore` needs `system`.
  Chosen: `18.4-system-trixie` + in-tree backups. The Barman Cloud
  Plugin is the stated future but is v0.14.0 (2026-07-29) — migration
  is a tracked follow-up, not a lab. Unlike ADR 005's ingress-nginx
  call, the incumbent path here is not EOL, merely no longer default.
- **Backup monitoring must watch the bucket, not the counters.**
  `pg_stat_archiver.archived_count` climbed and `ContinuousArchiving`
  read True while nothing reached S3 — CNPG's archive command exits 0
  when no destination is configured.
- **Backup credentials are node-scoped** (`inheritFromIAMRole` over
  IMDS): any pod on the node can reach the backup bucket. Accepted for
  throwaway lab data; IRSA is the correct answer and needs an OIDC
  provider kubeadm doesn't create.
- **The backup bucket must outlive the cluster.** It currently sits in
  the node stack with `ForceDestroy`, so `pulumi destroy` reaps the
  backups — fatal for Phase 8's rebuild-with-state drill. Separate
  lifecycle required before Phase 8.
- **ArgoCD Applications are still not GitOps-managed** (7.4 part 1: a
  fix committed to git changed nothing until applied by hand).
  App-of-apps is now a prerequisite, not a nice-to-have.
- Operator CRDs are megabyte-scale: Application needs
  `ServerSideApply=true` or the 256KiB last-applied annotation cap
  silently breaks the two largest CRDs.
- PLAN.md 7.4 is complete; 7.5 (capstone) proceeds on CNPG.

## What the hand-built detour was worth

Every row of the scoring table is legible only because we built the
other side first. "2 seconds" is a number; "2 seconds instead of the
three minutes we spent hand-typing RECONNECT into two pgbouncer pods at
midnight" is a lesson. The operator's value is not that it works — it's
which specific problems it makes structurally impossible, and that list
is only visible from the far side of having had them.
